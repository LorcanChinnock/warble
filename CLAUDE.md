# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Warble is a macOS 15+ app that shows what's playing in the notch and controls it. It's a SwiftPM package (Swift 6 language mode, strict concurrency) whose only Swift dependency is Sparkle; it also bundles mediaremote-adapter, a git submodule built with CMake. Its repository layout, tooling and release pipeline come from Shot (`LorcanChinnock/shot`); when you need a pattern this repo doesn't have yet, look there first. `docs/roadmap.md` lists the planned work, one GitHub issue per change.

## Mantra

By default, Warble is calm: a small, fast notch that shows what's playing and stays out of the way. Lyrics, the live waveform, stats and extra gestures are built in, but they start off.

- Nothing may slow the hover → expand path or a click on play/pause.
- When nothing is playing, Warble draws nothing and uses no CPU: no timers, no polling.
- The default is the simplest state, and every extra starts off.

## Who uses Warble

Design and write for the first person on this list; the later ones opt in to more.

- **The listener.** Wants play/pause, skip and to see what's on. Never opens Settings. Every default is set for them.
- **The podcast and audiobook listener.** Skips 15 seconds, changes the speed, sets a sleep timer.
- **The music fan.** Turns on lyrics and listening stats, switches speakers.
- **The multi-display user.** Uses the virtual notch on external displays and Macs without a notch, and sets rules per display.
- **The developer.** Uses the `warble` command, `warble://` links, Shortcuts and the MCP server.

What this means in practice:
- UI strings, Settings and the user guide speak to everyone. Avoid jargon (MCP, CLI, JSON) outside the developer-facing parts.
- Developer features stay in their own Settings card and guide pages, off by default.

## Commands

```bash
make test                         # WarbleModel and WarbleCore unit tests (Swift Testing)
make test-linux                   # WarbleModel tests in Docker on Linux, as CI runs them
make perf                         # PerfTests alone: the timed paths with budgets in docs/performance.md
make perf-app                     # scripts/perf.sh: the installed WarbleDev against its budgets; moves the pointer for ~5 min
make lint                         # scripts/lint.sh: bans patterns that caused bugs (see below); on macOS also scripts/strings.sh --check
make strings                      # sync Resources/Localizable.xcstrings with the strings the build extracted
make build                        # swift build
make bundle                       # build and sign build/WarbleDev.app only
make run                          # build, install to /Applications/WarbleDev.app, relaunch
cd site && npm run dev            # the website (see site/README.md)
swift test --filter <testName>    # one test, e.g. --filter notchSitsBetweenTheMenuBarAreas
```

- With only the Command Line Tools selected, the Makefile pins the newest 26.x SDK and adds the testing plugin path, so a bare `swift build`/`swift test` can fail on SwiftUI macros. Prefer `make`, or prefix with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`.
- Signing uses the `Warble Dev` certificate from `scripts/make-dev-cert.sh`, so permissions such as Automation survive rebuilds. Without it, `bundle.sh` signs ad hoc and warns.
- Logs: `/usr/bin/log stream --predicate 'subsystem == "dev.lorcan.Warble.dev"'` for WarbleDev, `dev.lorcan.Warble` for a release (in zsh, plain `log` is a builtin). Use `Logger.warble("category")` from `Sources/Warble/Log.swift`.

## Running and testing locally

Local builds are `WarbleDev.app`. A real installed version is `/Applications/Warble.app`, usually from Homebrew. Never install over, rename or delete `Warble.app`, or Homebrew loses track of it.

1. **Quit the installed release first:** `pkill -x Warble`. Both apps draw in the notch, so with both running their panels stack. `-x` matches the executable name exactly, so `pkill -x Warble` never kills WarbleDev, and `pkill -x WarbleDev` never kills the release.
2. **Run the dev build:** `make run` builds, installs `/Applications/WarbleDev.app` and launches it. Confirm the running binary with `pgrep -lf WarbleDev`. The ux-qa skill runs `build/WarbleDev.app` from `make bundle` without installing it.
3. **When finished, quit and uninstall the dev build,** then reopen the release if it was running:
   ```bash
   pkill -x WarbleDev
   rm -rf /Applications/WarbleDev.app build/WarbleDev.app   # or $INSTALL_DIR/WarbleDev.app if you set it
   open /Applications/Warble.app
   ```

## Architecture

Four targets:
- `Sources/WarbleModel`: logic that needs only Foundation, so CI builds and tests it on Linux: the app's state, `reduce` and their ports (`App/`), notch geometry, playback state and its interpolation, the hover state machine, source priority, the toast queue, the Doctor's checks, the lyrics parser, the query lyrics are looked up by and the line showing (`Lyrics`, `LyricsQuery`, `LyricsState`, `Lyrics/`). It may import CoreGraphics only inside `#if canImport(CoreGraphics)`. Linux Foundation has `CGFloat`, `CGPoint`, `CGSize` and `CGRect`, but not `CGPath`, `CGColor` or `CGImage`.
- `Sources/WarbleCore`: logic that needs Apple frameworks but no window, display or permission, including the real side of most ports: preferences, the now-playing sources, Core Audio volume and outputs (`SystemVolume`, `CoreAudioOutputs`), the last track's file (`LastPlayedFile`), the LRCLIB lyrics client and its cache in Caches (`LRCLIBClient`, `Lyrics/`), artwork colours and `TimerScheduler`.
- `Sources/Warble`: AppKit and SwiftUI that need a real session. `WarbleApp` is a `MenuBarExtra` with an `AppDelegate` adaptor; `Updater` wraps Sparkle. It draws the store's state, turns AppKit events into actions and carries out the effects that need AppKit, and decides nothing else.
- `Sources/WarbleCLI`: the `warble` command, a thin client of the running app's socket. It depends on WarbleModel only and decides nothing: it parses with `WarbleCommand`, sends the arguments and prints the answer.

**If logic can be tested without a window, it goes in WarbleModel with a test, or in WarbleCore if it needs an Apple framework.** Tests are top-level `@Test func` with sentence-style names: `Tests/WarbleModelTests` (run on Linux) and `Tests/WarbleCoreTests` (macOS). The app target has no tests.

The store: what the app decides lives in WarbleModel's `App/`. `AppState` holds it, `AppAction` is everything that can happen to it (a source's report, the pointer, a click, a key, a setting changing, a deadline coming due), and `reduce(_:_:now:)` is a pure function from a state and an action to the next state and a list of `AppEffect`s. The state machines (`HoverIntent`, `IdleAfterPause`, `ToastQueue`) are parts of `AppState`, so nothing decides around them, and the selectors `AppState.notchState(_:)` and `card(_:)` give each notch what to draw. A settle pass at the end of `reduce` brings whatever follows from the notches' states up to date, such as Idle being held off while one is open, and asks for each effect once when its reason changes. `Store` runs `reduce` synchronously on the main actor for each `dispatch`, so nothing sits between a hover or a click and the panel: no `Task` hop, no Combine and no async/await on that path. It then calls `onChange(old, new, action)` and arms one timer through the `Scheduler` port for `AppState.deadline`, the earliest of every part's deadlines, or none when nothing is due. That's where "no timers while nothing plays" is kept, and a test checks it. Effects are data. `EffectRunner` (WarbleModel) carries out the ones that go through a port, off the main actor where they're slow, and sends the answers back as actions; it hands the rest to `PlatformEffects` (`Sources/Warble/App`), which needs AppKit. Ports are protocols in `App/Ports.swift`: `WallClock`, `Scheduler`, `HotkeyRegistrar`, `DisplayProvider`, `VolumeControl`, `AudioOutputs`, `LastPlayedStore` and `LyricsProvider`, beside `NowPlayingSource`. Their real implementations live in WarbleCore or the app and their fakes in `Tests/WarbleModelTests/App/Fakes.swift`; add one only when a test needs a fake. `AppEnvironment` (`Sources/Warble/App`) is the composition root: `AppDelegate` builds it once and passes it down, and views read its objects from the SwiftUI environment (`View.inject(_:)`), so no type of Warble's own has a shared instance. Each target is split into feature folders (`App`, `Playback`, `Notch`, `Idle`, `Toasts`, `Doctor`, `Shortcuts`, `Displays`, `Volume`, `Design`, `Settings`), and CONTRIBUTING.md › Adding a feature lists what a feature adds.

Now playing: since macOS 15.4, only Apple-signed processes can read now-playing information through the private MediaRemote framework. Warble bundles ungive/mediaremote-adapter, BSD-3-licensed: `scripts/bundle.sh` builds it with CMake from the `Vendor/mediaremote-adapter` submodule and puts `mediaremote-adapter.pl`, `MediaRemoteAdapter.framework` and `MediaRemoteAdapterTestClient` in `Contents/Resources`, signed but never linked. `AdapterSource` (WarbleCore) runs `/usr/bin/perl <script> <framework> <test client> stream --micros` with absolute paths, since `/usr/bin/perl` is Apple-signed, and each command as its own short run (`send 2`, `seek <microseconds>`). The stream starts behind a small Perl watchdog (`AdapterSource.watched`) that forks, waits on stdin and stops the stream when stdin closes. Warble holds the only write end, so the stream ends with Warble even after `kill -9` or a crash. `AdapterStream` (WarbleModel) turns the stream's lines into a `PlaybackState`; its tests replay output recorded from Safari in `Tests/WarbleModelTests/Playback/Fixtures`. A tab reports WebKit's GPU process as `bundleIdentifier` and the browser as `parentApplicationBundleIdentifier`, so the parent wins. When the stream exits on its own, `AdapterSupervisor` (WarbleModel) runs `test`, which exits 0 when the adapter still works, before starting it again with a growing delay. `test` times out now and then on a working adapter (exit 3 or 4), so those are retried; other failures stop it until Warble is opened again. CONTRIBUTING.md › Updating the adapter explains how to bump the pin. When more than one app reports playback, `SourcePriority` (WarbleModel) picks the one the notch follows: a pinned app, else the one that started playing last, never one on the ignore list (video calls by default). It takes reports per bundle identifier, so it doesn't care how sources are found. Keep everything that touches it behind the `NowPlayingSource` protocol, so a macOS change means replacing one implementation. A source's reports come in as `.playbackReported`, and commands reach it only as the `.send` effect, which `EffectRunner` sends to its `source`; the preview track is `PreviewSource`. The protocol, `PlaybackState` and `PlaybackCommand` live in WarbleModel; `PlaybackState.elapsed(at:)` runs the position on from the last report, so the progress bar needs no timer of its own. When the adapter isn't bundled or `AdapterSource` gives up, which ends its `states`, `ScriptSource` (WarbleCore) follows Music and Spotify with AppleScript instead: it reads a player when the player posts its distributed change notification, scripts only a running player, and so asks for Automation permission only then. Never run `osascript` against an app without a timeout, and don't script QuickTime.

Settings: keys and defaults live in WarbleCore `Preferences`. Views read them with `@Setting(PreferenceKey.x)`, which takes the default `Preferences` registers, from the `SettingsStore` (`Sources/Warble/Settings`) in the SwiftUI environment; `NSView(hosting:settings:)` hands it to every hosted view. A test checks every such key has a registered default. `SettingsWindow` opens Settings from the menu bar menu, or when Warble is opened again from Finder: a sidebar of `SettingsSection`s beside a grouped `Form` of standard controls in the system appearance, not the notch's black. It takes a Dock icon while open and drops its content when it closes. Shortcuts has a row for each `WarbleAction` (`ShortcutRow`). `ShortcutRecorder` watches keys and clicks only while it records, and pauses `HotkeyCenter` meanwhile. `ShortcutRecording` (WarbleModel) decides what a pressed key does: cancel, clear, ask for a modifier, refuse a reserved or taken combo, or record it. `HotkeyCenter.start()` registers the shortcuts at launch and again whenever a `hotkey.*` key changes, exclusively, so macOS refuses one another app holds exclusively, and Settings shows it. Open at login is `LoginItem` (`Sources/Warble/Settings`), which reads and sets `SMAppService.mainApp` and stores nothing of its own, so it always matches System Settings › Login Items. A section or row arrives with its feature; Players comes later.

Design: Warble's look is Native, its own and not Shot's; don't bring over Shot's Brutal tokens or controls. The notch is pure black so it merges with the camera housing, with the system font, white marks and grey for anything secondary, and no accent colour. Its tokens live in `Native` (`Sources/Warble/Design/Native.swift`), beside `NSView(hosting:)` and `ScaledFont`, which follows Settings › General › Text size.

Doctor: `Doctor` (WarbleModel) turns facts into checks, each with a fix. The facts are the adapter's state, the macOS version, Automation for each scripted player and which players are open. Its words live in WarbleCore (`Doctor+Mac.swift`), which also asks macOS about Automation without prompting. `AppState.doctor` gathers the facts again only on events: the adapter going missing or giving up, a player opening or quitting, a script refused with -1743, and a notch opening. Each time `reduce` asks for `.gatherFacts` with a refresh number, so facts from an older refresh are dropped, and `PlatformEffects` gathers them. While the adapter works it asks macOS nothing. `DoctorModel` is what the cards draw, plus their fix buttons. While a check fails, every notch rests with a "!", even with nothing playing, and opens on a card (`NotchCard.doctor`, taller than the player's) that lists the checks.

Notch: `NotchController` (`Sources/Warble/Notch`) keeps a `NotchSurface` for each camera housing that `VirtualNotch.housings` (WarbleModel) returns: the built-in display's notch, and a virtual one at the top centre of each display without a notch whose `VirtualNotchRule` asks for one. By default only the main display gets one, and only while no display has a real notch (the lid is closed, or the Mac has none). Rules are stored per display UUID under `PreferenceKey.virtualNotch`, and the menu bar menu and Settings › General both set them (`VirtualNotchPicker`). Each surface puts its `NotchPanel` over its housing in a `NotchState`, at the frame `NotchLayout` works out, while `PlayerModel` holds what's playing once for all of them. The controller only turns displays, from the `DisplayProvider` port (`Displays`), and their rules into surfaces and dispatches `.housingsChanged`, again whenever either changes. In `Store.onChange` it copies the state into `PlayerModel` and `DoctorModel` and has each surface draw what `AppState` says for it (`NotchSurface.apply(_:)`, then `update`). The panel joins every Space, full-screen ones too, since a nonactivating panel at its level joins them whatever its collection behaviour asks. A full-screen app hides the notch on its display instead: `FullScreenSpaces` (`Sources/Warble/Displays`) reads each display's current Space type from the window server (`CGSCopyManagedDisplaySpaces`, looked up with `dlsym`, so without it no display counts as full screen), and `NotchController` dispatches `.fullScreenChanged` on `NSWorkspace.activeSpaceDidChangeNotification` and each layout, never on a timer. `AppState.Surface.isFullScreen` makes `notchState` Hidden, so the notch draws nothing and takes no hover, except a track-change toast with `PreferenceKey.toastsInFullScreen` on (it starts off), which shows and goes as usual while the panel lets clicks through (`ignoresMouseEvents`). With `PreferenceKey.hideFromCapture` on (it starts off), `NotchSurface.apply(_:)` sets each panel's `sharingType` to `.none` from `AppState.hidesFromCapture`, so the window server leaves the notch out of screen sharing, recordings and screenshots, ScreenCaptureKit's included (checked on macOS 15, 26 and 27), while it still draws for you. Nothing watches for a capture, so it needs no port, effect or timer. With `PreferenceKey.virtualTitle` on (it starts on, the one extra that does, since the middle of a virtual notch is otherwise empty), a resting virtual notch draws the title of what's playing in its middle, where a real one has the camera: `AppState.titleInNotch(_:)` is true for a virtual surface that isn't full screen while something plays, and `NotchSurface.apply(_:)` copies it to `NotchModel.showsTitle`. `TrackTitle` (WarbleModel, `Notch/`) cuts the tags a name collects ("- Remastered 2009", "(feat. …)", "[Live at …]", "(Official Video)") and picks "Title — Artist", the title or the title faded from widths `VirtualTitle` (`Sources/Warble/Notch/Views`) measures, so the notch stays `VirtualNotch.width` wide. A faded title scrolls to its end once for each track, in Core Animation (`NotchMotion.titleScroll`), never loops and never runs with Reduce Motion; `NotchModel.scrolledTitle` keeps it from scrolling again each time the notch closes over it. The text is a `CATextLayer`, since AppKit draws only the visible part of a text field, which would leave the end of a scrolled title missing. Such a surface's `notchState` leaves out the track-change toast (the title scrolling says the same, and lyrics take the strip), except over a full-screen app, where the title isn't drawn. macOS reports the housing to the half point, so its edges and height can fall on half points. AppKit snaps windows to whole points, so the panel's window grows out to whole points on both sides (`NotchLayout.window(for:)`) and draws its shape centred, at the housing's exact width and height. The resting corners and wings follow the housing's height (`NotchLayout.cornerRadius`, `wing`), so they stay the same physical size at every display scale; `Tests/WarbleModelTests/Notch/MeasuredHousings.swift` holds what a 15-inch MacBook Air reports at each scale. `HoverIntent` (WarbleModel) decides when the pointer opens a notch into Expanded, after `expandDelay` or at once on a click, and closes it again: it takes timestamped events and returns the next deadline instead of running timers. Each notch's lives in `AppState.surfaces`, which is `Notches` (WarbleModel, `Notch/`), a `Feature` like the rest: it handles the actions about the notches themselves, reads the other features' parts through `SharedState` (the toast, the lyric line, the Doctor's "!" and the demo's step, which it draws ahead of anything else), and works out `notchState`, `card` and `answersPointer` from them, so its deadline joins the store's one timer. A surface dispatches `.pointer` from a tracking area over only the camera housing while resting and the whole panel once open, and `.hover(_, .click)` for a click on the panel, which also closes any other open notch. Only while a notch is open does `reduce` ask for `.watchClicksOutside` (a global click monitor in `PlatformEffects`) and, with the pointer on it, `.takeEscape` (a temporary `HotkeyCenter` key through the `HotkeyRegistrar` port, so no permission is needed); both dispatch `.dismiss`. Between states the shape morphs on one spring while the content cross-fades; with Reduce Motion the shape changes at once and only the content fades. The panel grows before a morph and shrinks after it, so nothing is clipped. Expanded holds the playback controls. They dispatch `.command`, and `reduce` shows play/pause, a seek and the shuffle and repeat modes at once (`PlaybackState.playing(_:at:)`, `seeked(to:at:)`) and asks for `.send`; the app's next report replaces that guess. A podcast or audiobook, which `SpokenWord` (WarbleModel) tells from `PlaybackState.mediaType` or the app, has back 15 and forward 30 seconds in place of previous and next while `AppState.skipsBySeconds` says so: only with `PreferenceKey.podcastSkips` on (it starts off), and never for a live stream. They dispatch `.skip(by:)`, which `reduce` turns into a seek from the position now, kept within the track. The adapter can't set a chosen speed (its `speed` only steps the app's own list), so a speed control waits on #143. `SystemVolume` (WarbleCore) reads and sets the default output's volume through Core Audio. `reduce` asks for `.followVolume`, which listens for its changes, only while Expanded shows the player's card, and scrolling over the panel in any state dispatches `.scrolled` with the volume read just before, as `VolumeScroll` (WarbleModel) works out. Each scroll also carries its horizontal delta and its trackpad gesture's phase (`Swipe.Phase`, `nil` for a wheel). With `PreferenceKey.swipeToSkip` on (it starts off), `Swipe` (WarbleModel, `Gestures/`) in `AppState.swipe` decides each gesture's way from its first `Swipe.lockDistance` points: up and down goes to the volume, including what it held back, and sideways skips once at `Swipe.skipDistance` with `.send` and `.haptic`, by the fingers' direction whatever natural scrolling says. The coast after a sideways swipe does nothing, a wheel only scrolls, and with nothing playing a swipe sends nothing. It waits on events, so it has no deadline. With `PreferenceKey.dragArtOut` on (it starts off), `AppState.artDrag` gives what dragging the art out of the player's card carries, `ArtDrag` (WarbleModel, `Gestures/`): the image, named for the track, and `PlaybackState.link` where the source gives one. Only `ScriptSource` does, from Spotify's `spotify url` turned into an open.spotify.com link; the adapter reports none. `ArtDragArea` (`Artwork.swift`) lies over the art's button: a click still dispatches `.openApp`, and once the pointer moves 4 points it starts AppKit's own drag with one item, `ArtPromise`, a file promise for Finder that also carries the image data, the link and its text, so each app takes the form it uses. The drag dispatches `.hover(_, .dragging(true))` and `false`, so `HoverIntent` holds the card open, as for a menu, and `reduce` lets go of Escape so the key cancels the drag. To see the notch without playing anything, launch with `open build/WarbleDev.app --args -notchPreviewState resting`, which shows a preview track instead of reading the adapter, and hover or click it. Add `-notchPreviewVirtual YES` to draw the virtual notch instead, on a Mac that has a notch. A right-click or Control-click on any notch, in any state, opens `NotchMenu`: the app it follows, Settings, updates and Quit, so Warble can be reached with its menu bar icon off. `NotchPanel.sendEvent` takes the click before SwiftUI, and while the menu is open `HoverIntent` keeps a resting notch resting and `reduce` lets go of Escape, so the key closes the menu. `Toast` shows a short message near the bottom of the screen under the pointer. Notices that slide out of the notch, such as a track change, are another thing: `ToastQueue` (WarbleModel) decides which one shows and for how long, with no timers of its own. With `PreferenceKey.trackChangeToast` on (it starts off), `reduce` posts a `TrackToast` (WarbleModel) for each new track while no notch is open, and each resting notch draws it as `NotchState.toast`: the wings with the title and artist in a strip below, `NotchLayout.toastDrop` deep. Only the housing takes the hover, as at rest. Opening a notch, playback stopping or turning the setting off dismisses it. In the `resting` preview, next and previous change the preview track, so a shortcut for Next track shows the toast. `HotkeyCenter` registers the global shortcuts of `WarbleAction`, none of which has one by default. A press dispatches `.perform(action)`, which does what the matching button does, so the command line, links and Shortcuts need only an adapter. `WarbleAction.openNotch` opens the notch on the pointer's display with the keyboard in it (`HoverEvent.keyboard`, which pins it open). Only then does `NotchPanel` take key, and Warble comes to the front, since VoiceOver and Tab follow only the app in front. Warble has no menu bar of its own, and `NotchSurface` gives the app that was in front its place back when the notch closes, unless a click has moved on. Notch buttons use `.buttonStyle(.notch)`, so Space or Return presses the one with the focus ring. Keys no control used reach `NotchPanel.keyDown`, and `NotchKey` (WarbleModel) says what each does: Space plays or pauses, ← and → seek 10 seconds, ⇧← and ⇧→ skip, ↑ and ↓ change the volume, Esc closes.

Accessibility: every notch control has a VoiceOver name, and what's playing reads "Now playing: <title> by <artist>". Nothing is shown by colour alone: shuffle and repeat draw a dot when on, and each Doctor check gives its outcome as its value. Increase Contrast lightens `Native.secondary` and `Native.track` and swaps the glow for a border. A `Toggle` or `Picker` in a `Form` whose label has two `Text`s reports no name of its own, so give it `.accessibilityLabel` and the second line as `.accessibilityHint`, then check with the ux-qa `axdump`.

Lyrics: with `PreferenceKey.lyrics` on (it starts off), a resting notch shows the current lyric line in a strip below it, `NotchState.lyrics`, `NotchLayout.lyricsDrop` deep, below the toast in priority, so a track-change toast takes the strip while it shows. `LyricsState` (WarbleModel) in `AppState.lyrics` decides it: at the end of every `reduce` it takes the track shown (none while Idle) and asks for `.fetchLyrics` with a fetch number the first time a track plays, never for a pause, a seek or new art, and never for speech apps or a track with no length. `EffectRunner` asks the `LyricsProvider` port and parses the answer with `Lyrics(lrc:)` off the main actor, then dispatches `.lyricsLoaded`; an answer whose number isn't the latest is dropped, and turning lyrics off drops any on its way. While a line shows and the track plays, `LyricsState.deadline` is when the next line starts, worked out from the report and the rate, and joins the store's one timer, so there's none while paused, Idle or with no lyrics. `EffectRunner` drops a fetch whose turn comes after a newer one was asked for, so the latest is always asked. `LRCLIBClient` (WarbleCore) is the real provider: one request at a time, in order, and its cache in Caches is the only copy of any lyrics; they're never saved with the last track played. "No lyrics" expires after 30 days. Off, nothing is sent to LRCLIB. `LyricsLine` draws the line it's given. `LyricsState.excerpt` is the lines around the position (`LyricsExcerpt`: one before the line being sung, or the next to be, and three after, gaps left out), kept up to date with the line, and also while paused. While a song with lyrics shows (`AppState.hasLyricsCard`), the player's card has a lyrics button beside the output button, which dispatches `.showLyrics(display:, true)`. Then `AppState.Surface.showsLyrics` swaps the open card to `NotchCard.lyrics` until the notch closes, the way `showsDoctor` does. That card is the player's size and has the same button in the same place to swap back. `LyricsCard` draws the excerpt it's given. The `resting` preview uses `PreviewLyrics`, a hymn out of copyright, so it sends nothing.

Idle: after a pause, `IdleAfterPause` (WarbleModel) decides when the notch goes back to Idle: `PreferenceKey.stayVisibleAfterPausing` seconds (10 by default) after the pause, a new track or the pointer leaving. While the pointer is on a notch or a card is open it never goes Idle; playing again cancels the countdown, and a source that stops reporting goes Idle at once. Like `HoverIntent`, it takes timestamped events and returns the next deadline, and it's part of `AppState`, so its deadline joins the store's one timer, and there's none while playing or Idle. Before it, `reduce` keeps a report of nothing from hiding the notch for `AppState.hideDelay` (1.5 seconds), longer than the gap a source leaves between tracks, so a skip doesn't close the notch under the pointer.

Sleep timer: with `PreferenceKey.sleepTimer` on (it starts off), the player's card has a sleep timer button (`SleepTimerButton`) beside the output button, which dispatches `.setSleepTimer(SleepTimer.Choice?)`: 15 minutes, 30 minutes, 1 hour, End of track, or `nil` to turn it off. `SleepTimer` (WarbleModel, `SleepTimer/`) in `AppState.sleepTimer` holds the one running and its `deadline`, which joins the store's one timer, so there's none without a timer. A fixed timer's deadline is set when it starts; End of track's is worked out from `PlaybackState.elapsed(at:)`, `duration` and `rate`, again after each report, and a different track reported first counts as the end. At the end of every `reduce`, before `settle`, `followSleepTimer` ends the timer when `AppState.canSetSleepTimer` is false (setting off, Idle, a source gone, or a pause by hand or in the app, which cancels it), and when it's due guesses the pause (`PlaybackState.playing(false, at:)`), asks for the existing `.send(.pause)` and clears it. The button draws the time left from the deadline, like the scrubber, so nothing counts down in the store.

Welcome: on a first launch `AppDelegate` dispatches `.launched(firstRun:)`, from `Preferences.isFirstLaunch(saved:)`, which reads Warble's saved defaults domain: a Warble with `PreferenceKey.hasSeenWelcome` set, or with any other setting saved, was used before the window existed and never sees it. `Onboarding` (WarbleModel, `Onboarding/`) in `AppState.onboarding` starts the demo, then has `reduce` ask for `.showWelcome` once, when the demo ends (at once if something is already playing), and `PlatformEffects` opens `WelcomeWindow` (`Sources/Warble/Onboarding`): Open at login (`LoginItem`), the menu bar icon and a link to the guide, with no permission asked. Closing it saves `hasSeenWelcome` and dispatches `.welcomeClosed`. It decides nothing and has no deadline. The previews skip it, and to see it again run `defaults delete dev.lorcan.Warble.dev` and launch `WarbleDev`. The demo is `NotchDemo` (WarbleModel, `Onboarding/`) in `AppState.onboarding.demo`: resting with a track, Expanded on the player's card, then `NotchState.hint`, Idle with `NotchLayout.hintDrop` of "Hover here to see what's playing" below (`DemoHint`), each for the time `NotchMotion.demoResting`, `demoExpanded` and `demoHint` gives. It returns its next deadline like `IdleAfterPause`, which joins the store's one timer, so there's none once it ends. While it runs `Onboarding.notchState` and `card` give every notch its step ahead of anything else (`AppState.notchState(_:)` and `card(_:)` ask them first), and `NotchController` shows `DemoTrack` (`Sources/Warble/Notch/Views`) in `PlayerModel` from `AppState.demoTrackStart`, so `AppState.playback` stays what the sources said. A pointer entering a notch, a click, the Open notch shortcut, a menu or a report of something playing ends it at once (`endsDemo` in `Reduce.swift`), before the action meets the notch, so the notch carries on as usual.

Idle card: while Idle, each surface is in `NotchState.idle`, its panel exactly over the housing, black on a real one and on a virtual one whose rule is Always (`NotchHousing.isAlwaysShown`), and clear on any other virtual one (the panel sets `ignoresMouseEvents = false` so a clear panel still takes the pointer). Only the housing counts for the hover, as at rest, and `HoverIntent` opens it into Expanded with `NotchCard.idle`, as wide as the player's card and `NotchLayout.idleDrop` below the housing. `NotchState(_:isPlaying:needsAttention:idleHover:)` and `NotchCard(isPlaying:needsAttention:showsDoctor:)` (WarbleModel) decide which state and card each surface draws, through `AppState.notchState(_:)` and `card(_:)`; with `PreferenceKey.idleHover` set to `nothing`, Idle is Hidden and no panel shows, except over a housing set to Always, which stays a blank notch and ignores the pointer. The card shows `AppState.lastPlayed`. Whenever `LastPlayed.changes(from:to:)` says a report is a new track or new art, `reduce` asks for `.remember`, which `EffectRunner` answers off the main thread with the art shrunk to 112 pixels. An answer for a track that's no longer the latest is dropped, and the rest are saved with `.saveLastPlayed` through the `LastPlayedStore` port, `LastPlayedFile` (WarbleCore), to `LastPlayed.json` in Application Support. Saves are chained, so the latest wins, and the preview keeps it only in memory (`LastPlayedInMemory`). Resume dispatches `.command(.togglePlayPause)`; the art dispatches `.openApp`. Preview it with `open build/WarbleDev.app --args -notchPreviewState idle`, adding `-notchPreviewLastPlayed NO` for the card with nothing played yet.

Developer: Settings › Developer has a switch for each way in, all off by default, and `RemoteCommand` (WarbleModel, `Remote/`) is the one table of commands behind them: each gives the `AppAction` its button dispatches (`.perform`, `.command`, `.setVolume`, `.selectOutput`), so a command does exactly what the notch does. `warble://` links (`RemoteCommand(url:)`, both the `warble` and `warble-dev` schemes) arrive in `AppDelegate.application(_:open:)` as `.linkOpened`, which `reduce` does only while `AppState.answersLinks` is on (`PreferenceKey.answerLinks`), and `settings?section=` is the effect `.openSettings(section:)`; the section names in `RemoteCommand.settingsSections` must match `SettingsSection`'s raw values. The `warble` command is the `WarbleCLI` target, which depends on WarbleModel only and is bundled as `Contents/MacOS/warble-cli` (a `warble` there would collide with `Warble` on a case-insensitive volume; the Homebrew cask and `CommandLinkRow` link it). It sends its arguments as one `RemoteRequest` line over the Unix socket `agent.sock` in the app's Application Support folder (`RemoteSocketPath`), and `AgentSocket.Server` (WarbleCore) answers with a `RemoteResponse` line. The folder is 0700, the socket 0600, and each peer's user is checked. The server hands each request to `RemoteHandler` (WarbleModel) on the main actor, which parses it with the same `WarbleCommand`, dispatches the same actions and answers `now` with a `NowPlayingSnapshot` built from `AppState`; `output <name>` reads the `AudioOutputs` port to match the name (`AudioOutput.matching`) first. `AppState.listensForCommands` follows `PreferenceKey.commandLine`, and `settle` asks for `.listenForCommands(true)` or `false` once each time it changes, which `PlatformEffects` carries out by opening or closing the socket, so with it off no socket exists and with nothing sent the app does nothing. The command never opens Warble. Try it with `build/WarbleDev.app/Contents/MacOS/warble-cli now` while WarbleDev runs with the setting on, and note that a `defaults write` from Terminal reaches the running app only after it restarts, so turn settings on from the Settings window or before launching.

Motion: after `NotchSurface.apply(_:)` takes the store's state, `NotchSurface.update` sets `NotchModel.state`, `card` and `isPlaying` together inside one `Native.morph`, so every change of state or card, such as resuming from the idle card or playback stopping under the full card, morphs the shape and cross-fades the content; it grows the panel before the morph and shrinks it after, and `NotchPanel.show` lays the content out at the new size first so the shape stays centred. Content is keyed by `ContentID` and comes and goes with `ContentTransition`: in after `NotchMotion.contentDelay`, out in `contentOut`. What it shows is passed in as values, so content on its way out keeps the track that stopped. As the resting wings appear, the art grows from `NotchMotion.artScale` and `BarsView` raises the bars one after another (`NotchMotion.barDelay`) in Core Animation, then loops them at 8 fps; they drop as the notch leaves Resting, and their animations go with the view. The timings live in `NotchMotion` (WarbleModel). With Reduce Motion the shape changes at once and only the content fades.

Website: `site/` is the Astro site for warble.lorcanchinnock.com, deployed from each release's tag by `.github/workflows/site.yml`, which `release.yml` calls, so it describes the version people can install. Merging a site change to `main` doesn't deploy it (see `site/README.md` › Deploying). The user guide lives in `site/src/guide/`, one Markdown file per page at `/docs/<slug>/`, in file name order. Each file's front matter gives its `title`, a one-line `summary` and its `group` (the groups are in `site/src/lib/guide-files.ts`). Write pages as tasks, in second person: numbered steps, `<kbd>⌘⇧4</kbd>` for keys, and `> [!TIP]` or `> [!NOTE]` callouts. The site also renders `CHANGELOG.md` directly. The landing page's `#install` section holds the steps to open Warble past Gatekeeper, and the Homebrew cask's caveat (`scripts/homebrew-cask.sh`) links to it, so keep that anchor. release-please ignores `site/`. The site's look is Warble's own, not Shot's: black, quiet, gone when not needed. It uses the notch's black, white and greys in the system font, with no accent colour. Its one colour is a glow like the one the open card takes from the artwork, and light and dark follow the system. The tokens are at the top of `site/src/styles/global.css`. Only the footer's "LC_" mark and "Made by Lorcan Chinnock", the voice and the copy button carry over from Shot.

Performance: `docs/performance.md` holds the budgets, the reference Mac and how each is measured. `Perf` (`Sources/Warble/App/Perf.swift`) emits signposts in category `perf`: `Ready` at launch, and `Expand` and `Play/pause`, which run from the input to the next frame of the display after the change (`Perf.untilNextFrame`, one display link that goes away after it fires), so they cost nothing until someone touches the notch. `scripts/perf.sh` (`make perf-app`) drives the installed WarbleDev with the pointer through `scripts/perf-input.swift`, reads the signposts, and counts CPU and wakeups (context switches, the median 10-second slice) for the app and its Perl processes. A timer shows as wakeups long before it shows as CPU. `Tests/WarbleCoreTests/PerfTests.swift` (`make perf`) times the stream, artwork colours and idle-card art; `make test` skips it, and CI runs it on the release PR and on any PR labelled `performance`.

Concurrency: UI and model types are `@MainActor`. Heavy work runs in `Task.detached`.

## Rules enforced by `make lint`

- Use `NSView(hosting:)`, never `NSHostingView(rootView:)`/`NSHostingController`; a plain hosting view crashes when content changes under a visible window. `HostingView.swift`, which defines the helper, is exempt.
- Use `@Setting`, never `@AppStorage`; `@AppStorage` updates late, so views show inconsistent state.
- Don't use `onTapGesture(count: 2)` next to a single tap; every single click waits out the double-click interval. Use one `onTapGesture` and read `NSApp.currentEvent?.clickCount`.
- WarbleModel and its tests import only Foundation, Synchronization and Testing, plus CoreGraphics inside `#if canImport(CoreGraphics)`.
- Every `runs-on: macos-*` needs a `# macOS: <reason>` comment on the line above.

## CI

The repository is public, so GitHub's runners are free, but the free plan runs only 5 macOS jobs at once, so macOS runs can queue (`.github/workflows/ci.yml`):
- Every PR runs two required checks. `test` is Linux: `scripts/lint.sh` and WarbleModel's tests, which keeps WarbleModel portable. `macos` builds the app, checks the strings catalog, compiles for Intel, and runs every test except `PerfTests`, which it runs only on the release PR and on PRs labelled `performance`. On push to `main`, `warm-cache.yml` only builds, to save the Linux build cache PRs restore.
- release-please opens its release PR as the repository's GitHub App (`release.yml`), so its runs start without approval. The repository has auto-merge turned off: an admin merges the release PR by hand once its checks pass.
- `release.yml` runs `make test` on the tagged commit before it signs anything, because a `docs:`, `test:` or `ci:` commit merged after the release PR's checks can change what's released.
- Run `make lint` and `make test` before every push, plus `make test-linux` when you change WarbleModel, and push once per PR where you can, so CI is a check rather than a debugger.

## Conventions

- UI strings go through `Resources/Localizable.xcstrings` (CONTRIBUTING.md › Strings and translations). Pass literals to localizing APIs: SwiftUI views, or `String(localized:)` for AppKit titles and `String` properties. WarbleModel can't (no `String(localized:)` on Linux), so its labels live in WarbleCore. Logs and text that scripts read stay English. After adding strings, run `make strings` and commit the catalog; `make lint` and CI fail while it's stale.
- PR titles use Conventional Commits (`feat(notch): …`, `fix(player): …`). PRs are squash-merged and release-please generates versions and `CHANGELOG.md`, so never edit the version or tags by hand.
- Every PR links an issue or sub-issue: put `Closes #N` (or `Part of #N` when it doesn't finish the issue) in the PR body. Create the issue before starting any work, as a sub-issue of its release's umbrella issue.
- Any substantial change or new feature keeps docs in line in the same PR: the user guide in `site/src/guide/`, `README.md`, the landing page `site/src/pages/index.astro`, and `docs/roadmap.md` if it changes the plan. `CHANGELOG.md` is generated, so don't edit it.
- Only `make dist` builds `Warble.app` with the Sparkle feed. Every other build is `WarbleDev.app` (bundle ID `dev.lorcan.Warble.dev`, executable `WarbleDev`, scheme `warble-dev://`, no feed), so dev builds never self-update or replace the installed release. `scripts/bundle.sh` does the renaming.
- To QA UI changes by driving the real app, use the `.agents/skills/ux-qa` skill.
- For recordings that need a real player, `docs/demo/` is a made-up one with invented tracks and generated art (`docs/demo/README.md`). It's a separate package, outside every Make target and CI.
