# Developer

Read this before changing the `warble` command, links, Shortcuts actions, the socket or Settings › Developer. Back to the [architecture index](../../CLAUDE.md#architecture).

Settings › Developer has a switch for each way in except Shortcuts actions (below), all off by default, and `RemoteCommand` (WarbleModel, `Remote/`) is the one table of commands behind them: each gives the `AppAction` its button dispatches (`.perform`, `.command`, `.setVolume`, `.selectOutput`), so a command does exactly what the notch does. `warble://` links (`RemoteCommand(url:)`, both the `warble` and `warble-dev` schemes) arrive in `AppDelegate.application(_:open:)` as `.linkOpened`, which `reduce` does only while `AppState.answersLinks` is on (`PreferenceKey.answerLinks`), and `settings?section=` is the effect `.openSettings(section:)`; the section names in `RemoteCommand.settingsSections` must match `SettingsSection`'s raw values. The `warble` command is the `WarbleCLI` target, which depends on WarbleModel only and is bundled as `Contents/MacOS/warble-cli` (a `warble` there would collide with `Warble` on a case-insensitive volume; the Homebrew cask and `CommandLinkRow` link it). It sends its arguments as one `RemoteRequest` line over the Unix socket `agent.sock` in the app's Application Support folder (`RemoteSocketPath`), and `AgentSocket.Server` (WarbleCore) answers with a `RemoteResponse` line. The socket setup it shares with the [activities socket](activities.md) (`address(of:)`, the private folder and mode, the same-user check) is `UnixSocket`. The folder is 0700, the socket 0600, and each peer's user is checked. The server hands each request to `RemoteHandler` (WarbleModel) on the main actor, which parses it with the same `WarbleCommand`, dispatches the same actions and answers `now` with a `NowPlayingSnapshot` built from `AppState`; `output <name>` reads the `AudioOutputs` port to match the name (`AudioOutput.matching`) first. `AppState.listensForCommands` follows `PreferenceKey.commandLine`, and `settle` asks for `.listenForCommands(true)` or `false` once each time it changes, which `PlatformEffects` carries out by opening or closing the socket, so with it off no socket exists and with nothing sent the app does nothing. The command never opens Warble. Try it with `build/WarbleDev.app/Contents/MacOS/warble-cli now` while WarbleDev runs with the setting on, and note that a `defaults write` from Terminal reaches the running app only after it restarts, so turn settings on from the Settings window or before launching.

Shortcuts actions are App Intents in `Sources/Warble/Remote/Intents/`: Play or Pause, Next Track, Previous Track, Set Volume, Switch Sound Output and Get Now Playing. They have no Developer switch, since nobody runs one without building a shortcut first. Each calls `RemoteHandler.run(_:)` with a `RemoteCommand` (the same method `handle` uses for the command line, so the volume and output checks are shared), `selectOutput(id:)` for a picked output, or `nowPlaying()`. `AppEnvironment` registers the handler with `AppDependencyManager`, which the intents read with `@Dependency`, so no type gets a shared instance. SwiftPM doesn't write the `Metadata.appintents` that Shortcuts and Spotlight read, so `scripts/bundle.sh` runs `scripts/app-intents.sh`, which calls Xcode's `appintentsmetadataprocessor` on the release build's const values. After a change to an intent, check that `log show --predicate 'process == "linkd"'` mentions the app's bundle ID after a launch.

The names are stable before 1.0. `Tests/WarbleModelTests/Remote/CommandNamesTests.swift` lists every command with its name on the command line and its link route, so a rename fails it and has to be made on purpose. Change that list, `site/src/guide/33-command-and-link-reference.md` and the changelog together.
