# Settings

Read this before adding or changing a setting, the Settings window or Open at login. Back to the [architecture index](../../CLAUDE.md#architecture).

Warble has seven settings of its own. The first is Open at login: `LoginItem` (`Sources/Warble/Settings`) reads and sets `SMAppService.mainApp` and stores nothing, so the switch always matches System Settings › Login Items. When macOS refuses a change, `LoginItem.failedChange` holds what it tried, until a change works, and `failureDetail` replaces the switch's description with a line saying Warble couldn't turn it on or off and where to do it instead, with an Open Login Items… button. A Debug build is always refused, so that's the way to see it. The second is the title in a virtual notch, on at first: `NotchSettings` keeps it in `UserDefaults` (key `virtualTitle`) and dispatches `.virtualTitleChanged`, so `Notches.showsVirtualTitle` decides, in WarbleModel, which notch draws it (`AppState.titleInNotch`: a virtual notch, not over a full-screen app, while a track with a title shows). The third is how long a paused song stays, always at first: `NotchSettings` keeps `PauseDelay` in `UserDefaults` (key `pauseDelay`) and dispatches `.pauseDelayChanged`, which sets `IdleAfterPause.pauseDelay` (see [Idle](idle.md)). The fourth is when a virtual notch is there, only while playing at first: `NotchSettings` keeps `VirtualNotchVisibility` (WarbleModel) in `UserDefaults` (key `virtualNotch`) and dispatches `.virtualVisibilityChanged`, and `Notches.notchState` decides from it, for a virtual notch only (see [The notch](notch.md)). The fifth is how big the open card is: `NotchSettings` keeps `CardSize` (WarbleModel) in `UserDefaults` (key `cardSize`) and dispatches `.cardSizeChanged`, which sets `AppState.cardSize` (see [The notch](notch.md)). The sixth is the face of the notch's title, the system font at first: `NotchSettings` keeps `NotchFont` (WarbleModel) in `UserDefaults` (key `notchFont`) and dispatches `.fontChanged`, which sets `AppState.notchFont`; `Native.titleFont` makes the `NSFont`, and the artist and album stay in the system font. The seventh is the heart for Music's Favourites, off at first: `NotchSettings` keeps it in `UserDefaults` (key `favouriteHeart`) and dispatches `.favouriteHeartChanged`, which sets `Favourite.isEnabled` (see [The notch](notch.md#the-heart-for-musics-favourites)). The title and the resting bars always take the artwork's colour, which is no setting: `PlayerModel.tint` is `ArtworkColours.text`, a quarter of the first artwork colour and the rest white, which keeps at least 7:1 against the black notch whatever the cover, so there is no lightening and no Increase Contrast step. `PlayerModel` always picks the colours, for that and for the glow, which is always on. Those seven are the only settings the store holds. Everything else is fixed: the menu bar icon is always there and the notch's text is one size. `SettingsWindow` (`Sources/Warble/Settings`) opens Settings from the menu bar menu, the notch's right-click menu, or when Warble is opened again from Finder; all three call `show()`, which can also take a `SettingsTab` to open on, as both menus' About Warble does with `.about`. It's a standard preferences window, its own `NSWindow` rather than SwiftUI's `Settings` scene, because that scene can't be opened from AppKit, which the right-click menu and the reopen need. An `NSTabViewController` with the toolbar tab style holds three tabs, Notch, General and About, each a `SettingsTabController` hosting a SwiftUI view from `SettingsView.swift` (`NotchTab`, `GeneralTab`, `AboutTab`); the selected tab's name is the window's title. The window is 600 points wide and not resizable: each tab measures its own height (measured once off screen with `NSView.fittingHeight` so the window opens at the right size, then kept up to date with `onGeometryChange`), and the tab controller resizes the window to it when the tab changes. It reopens on the tab it last showed. Each tab is a `SettingsPage`: an optional header above a grouped `Form` (`.formStyle(.grouped)`) that doesn't scroll. The Notch tab's header is `NotchPreview` and a caption, then the six notch settings in three sections, as the [redesign spec](../redesign/spec.md#notch-tab) lays out: When a song is paused (Stay visible after pausing), Opened notch (Size, Song title font, Heart for Music's Favourites) and Displays without a notch (Show a notch, Song title in the notch), with a footer saying a MacBook's own notch never changes. The pop-up menus and switches are standard, and Size is a segmented control. A one-line row in a grouped form leaves its control reporting only its value, so Size and Song title font name themselves with `accessibilityLabel`. General has a Startup section with Open at login, with an Open Login Items… row while System Settings needs to approve it, and a Help section with link rows to the guide and its When nothing shows page. About is its own layout rather than a `SettingsPage`: a header with the icon, name, version and status line, with the status's button on the right, then an Updates form, two forms side by side for the Warble links and the acknowledgements (pulled 11 points into each other so the gap between them is the board's 18), and a centred footer; five quick clicks on the icon make it sing (`Chirp`). The status comes from `Updater.status`, an `UpdateStatus` (WarbleModel, tested) built from whether the build has a feed, whether a check is running (from Sparkle's `mayPerform` until it finds an update, finds none or fails), a version a scheduled check found, what the last check in this session found, and Sparkle's `lastUpdateCheckDate`. It says "Up to date" only after a check in this session found nothing; a check from an earlier session shows as "Last checked", and a build that has never checked shows no line. `UpdateStatus.label` (WarbleCore) words it, with `CheckDay` (WarbleModel) choosing today, yesterday or the date. The button is Check for Updates…, Try Again after a failure, Update… (the default button, in the yellow, `yellowDefaultButton()`) when a version is ready, Cancel while a check you asked for runs (`Updater.canCancelCheck`, which calls the cancellation Sparkle gave `UpdateUserDriver`), and none in a build with no feed or while a scheduled check runs, which can't be cancelled. The two switches come from `Updater.switches`, an `UpdateSwitches` (WarbleModel, tested): Check for updates automatically is Sparkle's `automaticallyChecksForUpdates`, and Install updates automatically is Sparkle's `automaticallyDownloadsUpdates`, which starts off and shows off and dimmed while automatic checks are off. Both are off and dimmed in a build with no feed. A failure says why, as `UpdateFailure` (WarbleModel, tested) sorts it from Sparkle's error code: a failure to reach the server or read its feed, or to download, says "Couldn't reach the update server. Check your connection.", and one after the download, while unpacking, verifying or installing, says "The update downloaded but couldn't be installed.", since checking the connection wouldn't help then. In a Debug build, `-updateStatusPreview checking|ready|upToDate|lastChecked|failed|failedInstall|off` shows that status line, since a dev build has no feed. Update… and Check for Updates… open the update window, below. A row that opens a web page is a `LinkRow`: the whole row is the link, with what it opens and an arrow in secondary text, and VoiceOver reads it as a link with that text as its value. Add a setting as a standard `Toggle`, `Picker` or `LabeledContent` row in a tab's form, and a link as a `LinkRow`. A row whose label has a second line names itself with `described(_:_:)` (see [Accessibility](accessibility.md)), and a switch or segmented control takes the icon's yellow with `accentSwitch()` (see [Design](design.md)). The window takes a Dock icon while open, and drops its tabs when it closes, so nothing in them keeps observing the login item or updates. `NotchPreview` draws a virtual notch at the real notch's proportions, scaled down, from the real views, `RestingContent`, `ExpandedContent` and `NoteContent`, so it can't drift from the notch. They read a `PreviewNotch`, a `PlayerModel` and `NotchModel` of its own whose dispatch does nothing, and they are not hit-testable, so a control in the preview never reaches the real player. It shows what's playing (the shared `PlayerModel`, while `showsPlayback`) with its real title, artist, album and artwork, or `NotchDemo`'s made-up song with generated art when nothing is. It rests with the art and bars, shows the title when the switch is on, and opens into the card when the pointer reaches it, with `Glow`. It stays open after the pointer leaves, so a change to a setting shows without pointing at it again, and a click, or a press from the keyboard or VoiceOver, closes it. With the heart switch on, the card shows the heart, filled when the live song is a Music favourite and an outline otherwise, the made-up song included. A change to the title font, the card size or the heart switch also opens the card for `peekLength`, 2 seconds, so the change shows without pointing at the preview; it closes by itself unless the pointer reaches it first, a card that's already open stays open, and under Reduce Motion it doesn't open by itself. With the virtual notch Off it fades the notch out and leaves the bare screen. A change to the pause delay or the virtual notch's visibility pauses the song (flat bars, a play button on the card) and, after `PreviewEnding.beat`, ends it as `PreviewEnding` (WarbleModel) decides: the paused song stays with Always, otherwise an empty notch that opens the note with the virtual notch Always, or the bare screen. The beat is the same for 10 seconds and 1 minute, so the preview never suggests a shorter wait. That end holds until the pointer leaves the preview or the title switch, font or size changes, then the song plays again. The beat's and the peek's sleeps are the preview's only timers, apart from the scrubber's while the card is open and the song plays (the card is only in the view while open, and the made-up song's clock restarts each time it opens); they run in `.task`s that end with the window. The preview sits on a pastel strip, a fixed gradient from the spec that is the same in light and dark, 10 points round with a hairline edge, so the black notch stands out. The preview lays the notch out at full size and draws it at `NotchLayout.previewScale` (WarbleModel, tested), the scale that fits the open card at Large, 221 points tall at full size, and 10 points below it into the strip, and never more than life size. Settings' strip is 240 points tall, so the notch is drawn at life size; at 150 points, about 0.63, it was too small to judge a change by. The first-run window passes `height: 150`, where the card is the whole point and the window stays compact. Every state shrinks by the same amount, so the three sizes still differ when the card opens; the menu bar band behind it is the housing's scaled height.

### The first-run window

`FirstRunWindow` (`Sources/Warble/App`) is the one window Warble opens by itself at launch, as the [redesign spec](../redesign/spec.md#first-run) lays out: the preview with the card held open (`NotchPreview(holdsOpen: true)`, with the Notch tab's settings and the virtual notch drawn as Always), the title as a heading, a line on what Warble does, an Open Warble when you log in switch on `LoginItem`, and a footer with where Settings is and Done, the default button. It's 500 points wide, fits its content's height (measured with `NSView.fittingHeight`, then refitted with `onGeometryChange`, keeping its top edge, when the switch's line becomes an error), has only the close button and no visible title, and Escape closes it. On a Mac with no display that has a notch (`NSScreen.notchDisplays`, so `-notchPreviewVirtual YES` counts too), the line says Warble draws one at the top of the screen. Whether it opens is `FirstRun.opens(storedKeys:)` (WarbleModel, tested), which `AppEnvironment` asks first thing, before `Updater` starts Sparkle, from the keys in the app's persistent domain only: Sparkle's `SUHasLaunchedBefore`, which every release has stored on its first start, Sparkle's other keys, the six settings keys, or the window's own `firstRunShown` keep it shut, so it never opens for someone updating. `firstRunShown` is stored as soon as it decides to open, so quitting with it open doesn't bring it back. `AppDelegate` builds it after the notch and drops it when it closes, which also drops its views, so nothing stays observing the login item. It takes a Dock icon while open (`DockIcon`'s `.firstRun`). It doesn't ask for the Automation permission; the system asks when `ScriptSource` first needs it. In a Debug build, `-firstRunPreview YES` opens it for that launch without touching the stored settings.

### The update window

`Updater` (`Sources/Warble/App`) builds Sparkle's `SPUUpdater` with Warble's own user driver, `UpdateUserDriver` (`Sources/Warble/Update`, ported from Shot's), and starts it only in a build with a feed. The driver draws `UpdateWindow`, a standard window titled Software Update with only the close button, for a check you asked for, the offer, the download and the relaunch, as the [redesign spec](../redesign/spec.md#update-window) lays out. It hands three things to Sparkle's `SPUStandardUserDriver`, which still shows them as its own alerts: the first question about checking automatically, "You're up to date", and errors. Its states are `UpdatePhase` (WarbleModel, tested): Checking (only after Check for Updates…), the offer, Downloading, a short Preparing while Sparkle unpacks it, Ready to relaunch, Installing, and Installed while running. `UpdateWindowModel` holds the state for the SwiftUI view, and `UpdateWindowLabel` (WarbleCore) words what depends on the update. The window is 540 points wide for the offer and 500 for the rest, fits its content's height, keeps its top edge where it is as the state changes, and takes a Dock icon while it's open (`DockIcon`, shared with Settings and the first-run window, so the icon goes when the last of them closes).

The offer is an `UpdateOffer` (WarbleModel, tested) from Sparkle's appcast item and update state: the versions, the download's size, how far Sparkle got, and whether it's critical, a major upgrade or a page to read. `UpdateOfferButtons` decides its buttons as Sparkle's own window did: Skip This Version, hidden for a critical update; Remind Me Tomorrow, which is Sparkle's dismiss and waits for the next daily check, so it's hidden while automatic checks are off, and reads Install on Quit once the update is already unpacked; Install and Relaunch, or Learn More… for a page; and the "Install updates automatically from now on" checkbox, which is About's Install updates automatically and shows only while Sparkle may install by itself. The release notes are `ReleaseNotes` (WarbleModel, tested). The release workflow embeds this release's GitHub release body and the 9 before it, each under its `## [version]` heading; `ReleaseNotes` reads each version's groups (Features shows as New, Bug Fixes as Fixed, Performance Improvements as Faster) and changes, drops release-please's links, scopes and commit hashes, and `since(_:)` keeps the versions above the installed one, or all of them when the installed one is older than every version listed. The box is 230 points tall and scrolls, and shows each version's number only when there's more than one.

What each choice does is `UpdatePhase.closing`, which the close button and Esc both follow: closing the offer is Remind Me Tomorrow, closing Checking cancels it, closing the window while it downloads only hides it and the download goes on, closing Ready is Later, which installs the update the next time Warble quits, and closing Installed while running is Later, which does nothing. Install and Relaunch downloads and then shows Ready, with Later and Relaunch Now, even if the window was closed meanwhile. A scheduled check's offer sets `Updater.pendingVersion`, which the menus show, as a dot on the menu bar icon (`NSImage.menuBarIconWithDot`) and Update to <version>… in place of Check for Updates…, because a menu bar app's window can open behind others; it's cleared once the offer's window is key while Warble is active, or once it's answered. Near launch it takes the keyboard, otherwise it appears without taking it, and behind Warble's own windows while one is in use. Installed while running replaces the alert `Updater` used to show: before Sparkle offers an update, `shouldProceedWithUpdate` compares the version on disk with the running one, and if another installer replaced Warble it stops Sparkle with `installationCanceledError` and shows that state, whose Relaunch opens the new copy (`Updater.relaunch()`). While an update downloads, whether or not its window is open, the menus' update item shows its progress, Downloading <version> (53%)…, read from the window's model by `Updater.menuItem`, and choosing it brings the window back. A download cancelled, failed or otherwise ended closes the window, which moves the phase off downloading, so the item goes back to Check for Updates…. The menu bar icon reads only `pendingVersion`, so the download's progress never redraws it. In a Debug build, `-updateWindowPreview offer|checking|downloading|ready|installed` shows the window in that state with made-up details, and its buttons only close it. `-updateWindowPreview downloading` leaves the menus showing that download once the window is closed, and `-updateStatusPreview ready` also shows a waiting update: the icon's dot and the menus' item.
